## Executive Summary

BITS (Biometric Integrated Tracking System) is an enterprise attendance management and payroll derivation platform engineered to automate timekeeping across multiple company branches. Operating with physical ZKTeco biometric fingerprint and facial recognition scanners, the system autonomously calculates tardiness, undertime, night differentials, and overtime hours.

The system features:
- **4 Role-Scoped Portals**: Dedicated access tiers for Super Admins, HR Managers, Department Supervisors, and Employees.
- **25 Relational Database Models**: Normalised PostgreSQL schema tracking departments, flexible shift matrices, approval hierarchies, biometric device logs, and immutable audit trails.
- **Team Scale**: Built collaboratively by an 8-person engineering team over a 6-month development lifecycle.

> **Production Deployment**: Replaced manual spreadsheet timekeeping and paper overtime forms with an automated, auditable, hardware-integrated pipeline across Avega Bros. Integrated Shipping Corp. terminal branches.

## Core Technical Contributions

While the broader team managed frontend UI layouts and employee onboarding workflows, my core responsibility was the **attendance computation, overtime routing engine, and relational integrity layer**.

### 1. Biometric Overtime Disambiguation State Machine
Physical biometric scanners operate as dumb loggers: whenever a fingerprint or face is recognized, the hardware writes an isolated record: `{ employeeId, timestamp, deviceId }`. 

In real-world operations, daily schedules frequently include overtime:
- Scan 1 (08:00): Regular Shift In
- Scan 2 (12:00): Lunch Out
- Scan 3 (13:00): Lunch In
- Scan 4 (17:00): Regular Shift Out
- Scan 5 (18:00): Overtime Shift In
- Scan 6 (21:00): Overtime Shift Out

**The Problem**: Naive attendance algorithms assume a maximum of two or four punches per day. A fifth scan either overwrote the regular check-out timestamp (causing severe undertime penalties) or threw an unhandled duplicate key exception.

**The Solution**:
I architected a deterministic event state machine that correlates incoming punch sequences against approved employee schedule requests:

```typescript
// Conceptual punch classification pipeline
async function processPunchLog(punch: BiometricPunch, employeeShift: ShiftAssignment) {
  const existingAttendance = await getAttendanceForDate(punch.employeeId, punch.timestamp);
  
  if (!existingAttendance.regularCheckOut) {
    // Normal shift lifecycle
    return resolveStandardShiftPunch(existingAttendance, punch);
  }

  // Shift is closed: determine if an approved Overtime Request covers this timestamp
  const approvedOT = await findApprovedOvertimeWindow(punch.employeeId, punch.timestamp);

  if (approvedOT) {
    return routeToOvertimeSession(approvedOT, punch);
  }

  // Fallback: Flag unassigned punch for HR supervisor review
  return flagOrphanedPunch(punch, "Unscheduled Post-Shift Punch");
}
```

- If an approved Overtime Request exists for the employee on that date, punches following shift closure are routed into a dedicated `OvertimeSession` record.
- If no approval exists, the punch is marked as an "Unscheduled / Unassigned Event", preventing data corruption while prompting the supervisor for resolution.

### 2. Midnight Boundary & Split-Shift Normalization
A frequent point of failure in attendance software occurs when a shift begins on one calendar day and terminates on the next (e.g. 10:00 PM to 06:00 AM). 

- **Calendar Boundary Bug**: Querying punches strictly by `WHERE date = CURRENT_DATE` resulted in the morning checkout being assigned to the following day as a premature check-in, leaving Day 1 without a checkout and creating a phantom "absent" record for Day 2.
- **Algorithm Fix**: Shifted query boundaries from calendar dates to **dynamic shift windows** (from 2 hours before scheduled shift start to 4 hours post-shift). Punches falling into this sliding window are bound to the parent shift ID regardless of calendar rollover.
- **Night Differential Derivation**: Automated the extraction of hours worked between 10:00 PM and 06:00 AM to calculate statutory night differential compensation accurately.

### 3. ACID Batch Operations for Department Approvals
When a department supervisor approves 50 overtime requests simultaneously before a payroll cutoff, partial failures (e.g., one employee having a conflicting schedule lock) can cause dangerous discrepancies between the approval logs and the final payroll ledger.

- Implemented **PostgreSQL Serializable Transactions** wrapped in Express service layers.
- If any validation rule fails within a batch payload, the entire transaction rolls back cleanly with detailed error reporting, ensuring zero orphaned financial records.

## Retrospective & Key Takeaways

1. **Defensive Hardware Integration**: You cannot trust raw hardware data. Biometric terminals frequently send duplicated events within 500ms when employees rest their finger on the sensor. Adding a software debouncing window (ignoring duplicate punches within 60 seconds) eliminated thousands of garbage events.
2. **Audit Trails Are Mandatory**: In payroll and timekeeping systems, records must never be hard-deleted. Every adjustment by an HR admin is recorded with author IDs and timestamped justifications.
3. **Collaboration at Scale**: Coordinating database schema migrations across 8 developers taught me the necessity of strict migration scripts, branch discipline, and API contract testing.
